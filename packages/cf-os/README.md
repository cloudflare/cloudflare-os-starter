# cf-os

The command line for a self-hosted [Cloudflare OS](https://github.com/cloudflare/cloudflare-os): it scaffolds a project from the [starter](https://github.com/cloudflare/cloudflare-os-starter), configures its `deployment.jsonc`, checks and deploys it, and drives the running instance through its API.

```sh
pnpm cf-os init                  # inside a project: configure it, then offer to deploy
pnpm cf-os check                 # validate, check the account, test, build, dry-run every deploy
pnpm cf-os deploy                # the same, then deploy for real
pnpm cf-os secrets               # set the optional Gatekeepers' OAuth credentials
npx cf-os init my-os             # no clone yet: create one in ./my-os, then the same init
npx cf-os@latest update          # inside a project: merge the starter's latest into it
npx cf-os@latest update --upstream  # any repository pinning Cloudflare OS: stage upstream's main
pnpm cf-os api list-gadgets      # call the running instance's API: here, list its workspaces
```

Inside the starter it is the `packages/cf-os` workspace package, and `pnpm cf-os <command>` runs it: fork or clone the starter, `pnpm install`, then `pnpm cf-os init`. `npx cf-os init` is for when you have not cloned it yet. It clones the starter's `main` branch (`--ref <branch>` and `--template <url|path>` pick another branch or a fork), installs, offers to create a private GitHub repository for it, and runs the project's own `pnpm cf-os init`.

## Commands

| Command | What it does | Account |
| --- | --- | --- |
| `init [<dir>]` | Outside a project: clones the starter into `<dir>` (`origin` renamed to `starter`), installs, offers to create a private GitHub repository with `gh` and push to it (running `gh auth login` first if needed), then configures it. Inside one: offers the `cf` sign-in, configures it as a new deployment or as the takeover of a hosted instance, and, once nothing is left as a placeholder, offers the Wrangler sign-in and to deploy. It asks which Gatekeepers to deploy beside Context, Scheduler and Web Search, preselecting those a taken-over instance runs, and, once you choose to deploy, each new OAuth one's credentials, which the deploy sets. Until the file is written, Esc goes back a question. `--template`, `--ref` and `--out` | Reads; creates the Access application and a One-time PIN provider, sets Gatekeeper secrets, and deploys, only if you choose to |
| `import [<instance>]` | Finds what a hosted-deploy instance runs and prints the `deployment.jsonc` values that redeploy over it, including `gatekeepers.<slug>.name` for each optional Gatekeeper it found. `--out <path>` writes them | Read-only |
| `access [--dry-run]` | Finds or creates the Access application for the router's hostname, and writes `access.issuer` and `access.audience` | Creates one application, unless one already names the hostname. A wildcard one covering it is reported, not reused |
| `secrets [<slug>...]` | Asks for, masked, the OAuth credentials an optional Gatekeeper's Worker lacks (every selected one by default) and sets them with `wrangler secret bulk` on stdin, never argv or a file. Prints the names set as JSON. Never creates a Worker; without a terminal, names the `wrangler secret put` commands | Sets secrets on existing Gatekeeper Workers; never creates one |
| `check` | Validates the file, checks the account has what it names, runs the tests and builds, dry-runs every deploy, and warns, without failing, about optional Gatekeeper secrets not set yet and an unset `MCP_PORTAL_URL` | Read-only |
| `deploy` | The same, then deploys every Worker. No confirmation. On the unconfigured template at a terminal, offers `init` first and then carries on | Deploys |
| `update` | Merges the starter's `main` into the project, fetched from its URL (no remote needed), checks the `cloudflare-os` submodule out at the pin it brings, runs `pnpm install`, and writes `.cf-os/update.md`: both commit ranges, the commits that change the Gatekeeper contract, any conflicts (left to git), and steps for a coding agent to finish and summarise the update, in the order the work usually goes (install and catalog, then Gatekeepers). When the root `package.json` has an `api:generate` script, as the starter's does, it then runs `pnpm run api:generate`, which regenerates [`cf-os api`](#driving-an-instance-cf-os-api)'s files under `packages/cf-os/src/api/generated` from the new pin: it leaves them unstaged, next to a staged pin, for review with it, and the brief lists the API commands added, removed and changed since the commit the update started from (`--since <commit>`), even when the merge brought the files already regenerated. A failed generation is one of the problems left to do, and the pin stays as it is. `--upstream` then moves the submodule on to upstream's `main`, staged and not committed, for review, with the merge itself committed. `--to <ref>` does the same for a given commit, tag or branch on `main`: one with green CI, the fix for a broken `main`, a step part of the way, or an older commit, which the brief treats as a rollback. With `--preview`, `--to` also takes an upstream branch or pull request (`pull/796`; `#796` only quoted, as a shell reads the rest of the line after `#` as a comment) that is not on `main`, for a merge request's preview deploy: the brief says to commit it on that branch only, lists any commits the current pin has that the branch lacks, and says to move the pin to `main` before merging. In any other repository that pins Cloudflare OS (no `deployment.jsonc` at its root), it moves the pin alone: `--upstream` is required, nothing is merged, and the brief points at the guide on the starter's `main`. The submodule is the one `.gitmodules` points at upstream with, or `--submodule <path>`. `--ref`, `--template` and `--dry-run` | None |
| `api [public] <command> [<arguments>]...` | Calls the running instance's API, the one its frontend uses, with commands generated from the pinned `cloudflare-os`: each command calls a method on what the one before returned, so `open-gadget <id> get-chat-history <chatId>` reads a workspace's chat; `api search "<task>"` finds the command line for a task. See [Driving an instance](#driving-an-instance-cf-os-api). `--url`, `--auth`, `--username`, `--dry-run`, `--timeout` and `--out` | None: it acts on the instance, as the user it signs in as |
| `install [--check]` | Installs the `cloudflare-os` submodule's own workspace; the root `postinstall` runs it | None |

Every command takes `--config <path>` (default: `deployment.jsonc` in the project root; `api` reads the instance's origin from it), `--account <id>` (the account `init` and `import` use, ahead of the file's `accountId`; `check`, `deploy`, `access` and `secrets` refuse one other than the file's), `--profile <name>` (passed to every `cf` call), and `--help`. It works from any directory inside the project.

Optionally, instead of signing in, set `CLOUDFLARE_API_TOKEN` to a token with Access: Apps and Policies Edit and Access: Organizations, Identity Providers, and Groups Read (Edit, for `init` to add a One-time PIN provider), plus Read on Workers Scripts, Workers KV Storage, Workers R2 Storage, AI Gateway, Zone and DNS.

## Output and prompts

Results meant for scripts are JSON on stdout: `import`'s values, `access`'s issuer and audience, the names of the secrets `secrets` set, the request a `--dry-run` would send, and what `update` did (whether the pin moved and was staged, the merge, the install, `api:generate`'s outcome, the brief's path and anything left to do; it exits 1 when something is left, even with the pin moved). Its `api` field is null when the root `package.json` has no `api:generate` script, `{"status": "generated", "files", "added", "removed", "changed"}` when it ran (the files it rewrote, and the API commands as space-joined paths such as `open-gadget get-chat-history`), `{"status": "failed"}` when it failed, which is one of the problems, or `{"status": "not-run"}` when the install did not complete. `cf-os api` prints its result as JSON, a subscription's events as JSON lines, and a byte stream as bytes. Without a terminal, `update` holds back `pnpm install`'s output and shows only its end, if it fails. Everything else goes to stderr. Exit codes are 0 for success, 1 for failure, and 130 for a cancelled prompt.

Questions are asked only when stdin and stdout are both terminals and `CI` is unset, the same rule `cf` follows. At a terminal, a step waiting on Cloudflare shows a spinner. Every question has a flag or config equivalent. Without a terminal, a missing answer fails and names the flag to pass, and `init` points at `import` and `access` instead, or at editing `deployment.jsonc` by hand: `init`'s Gatekeeper question is the file's `gatekeepers` block and `customGatekeeper.enabled`. `secrets` names the `wrangler secret put` commands, which ask for each value themselves.

## Driving an instance: `cf-os api`

`cf-os api` calls a running instance's [Cap'n Web](https://github.com/cloudflare/capnweb) API, the one its frontend uses, so an agent can list workspaces, read chats, approve actions and open Gatekeeper sessions without a browser. Its commands are not written by hand: they are generated from the pinned `cloudflare-os/packages/workshop-shared/src/api.ts`, so they are always the pin's.

```sh
pnpm exec cf-os api search "list chats"                         # the commands for a task, whole command lines as JSON (connects to nothing)
pnpm exec cf-os api --help                                      # the commands there are once signed in (connects to nothing)
pnpm exec cf-os api whoami                                      # who the session signed in as
pnpm exec cf-os api list-gadgets                                # the workspaces
pnpm exec cf-os api open-gadget <id> get-chat-history <chatId>  # a chain: open-gadget returns the workspace
pnpm exec cf-os api open-gadget <id> list-actions --options '{"filter": "pending"}'
pnpm exec cf-os api open-gadget <id> approve-action <actionId>  # acts on the instance, like the button
pnpm exec cf-os api open-gadget <id> subscribe-to-chat --timeout 60  # events, one JSON line each, for a minute
pnpm exec cf-os api public get-server-config                    # PublicApi, without signing in
pnpm exec cf-os api open-gadget <id> get-chat-history <chatId> --dry-run  # the calls, as JSON; connects to nothing
pnpm exec cf-os api whoami --url http://localhost:8787 --username <name>  # a dev server; the password from CFOS_API_PASSWORD
```

`search "<task>"` is where to start: it ranks the commands by the task's words and prints the best five as JSON, `[{"command", "summary"}]`, each a whole command line from `cf-os api` with a placeholder for every argument along the way; `pnpm exec` runs it without `pnpm`'s own lines around the output. Commands are the API's methods in kebab-case, starting from what a signed-in session gets (`AuthenticatedApi`); a leading `public` starts from `PublicApi` instead, without signing in. Required parameters are positional, in order; optional ones are flags named after them (`--before-sequence`), or `--arg-<name>` where that would clash with one of `api`'s own. Numbers, booleans, bigints and ISO 8601 dates are typed as they are; objects and arrays as JSON, inline, from `@file` or from `-` (stdin); where a string is one of the types (a chat message: `<text|json|@file|->` in the help), a word that is not JSON is that string, so `new-chat hello null` sends "hello", but text that starts with `@`, is `-` or is JSON (`42`, `true`) has to be quoted as a JSON string (`'"@alice, look"'`); bytes as `@file`, `-` or `{"base64": "..."}`. A command that returns a capability (`→ Overseer` in the listings) goes on to the next command, on it, and the whole chain is sent at once, pipelined in one session. A chain that ends on a capability sends nothing: `cf-os api new-gadget` creates no workspace, and fails saying so and naming a way to finish it (`cf-os api new-gadget get-metadata`). `--help` after any command prints the help of what was reached so far, and a command returning a capability lists that capability's commands too.

The result is printed as JSON on stdout: bigints as decimal strings, bytes as `{"base64": "..."}`, dates as ISO strings, and a capability inside it as `{"$capability": true}`. A `subscribe-*` command prints each event as a line `{"event": "<method>", "args": {"<parameter>": ...}}`, its arguments keyed by parameter name, until `--timeout <seconds>` (exit 0), Ctrl-C (exit 130) or its reader going away (`| head -n 1`, exit 0), and then unsubscribes; any other command given `--timeout` fails when it runs out. A returned byte stream goes to `--out <file|->`, or to stdout when that is not a terminal; a parameter that takes one reads a file or `-`. After a command returning an untyped capability, `call <method> [json-args...]` calls a method by name, unchecked. Everything the chain made is released when it ends, however it ends. A usage error exits 2, and means nothing was sent: fix the command rather than retry it. A failure of the call exits 1. Either way the message is on stderr.

The instance is `--url <origin>`, else the deployment file's public origin (honouring `--config`); its API is the WebSocket at `wss://<host>/api`. An `http://` `--url`, for a local dev server such as `cloudflare-os`'s `pnpm dev-server` on `http://localhost:8787`, connects over `ws://`. The sign-in is `--auth <mode>`, or, without it, `password` when `--username` is given, `token` when `CFOS_API_TOKEN` is set or the origin is `http://` (Access fronts only `https://` origins, and `--auth access` refuses an `http://` one), and `access` otherwise:

| Mode | Credential | For |
| --- | --- | --- |
| `access` | A Cloudflare Access token: `CF_ACCESS_TOKEN`, else what `cloudflared access token -app=<origin>` prints once `cloudflared access login <origin>` has run. It is sent with the instance's own Origin, and the session signs in as the Access identity | An instance behind Access, as the starter deploys it |
| `token` | `CFOS_API_TOKEN`, an auth token, the kind a password sign-in returns and the frontend keeps | A dev server, a test harness |
| `password` | `--username <name>` and `CFOS_API_PASSWORD`, hashed as the frontend hashes it | A dev server, a test harness |

Secrets come from the environment or `cloudflared`, never from the command line, and the methods that take credentials (`PublicApi`'s sign-in methods, `change-password`) are not commands. When the connection does not open, a plain request to the same URL says why: an Access refusal or redirect names `cloudflared access login <origin>`. `--dry-run` prints `{"url", "auth", "on", "chain"}`, the calls with their decoded arguments, and runs nothing: it connects to nothing, runs no `cloudflared` and hashes no password, and `auth` is only the mode and any username.

The generated files are `src/api/generated/schema.json` and `commands.ts`, committed. `pnpm api:generate` rewrites them from the pin, printing what changed as JSON, its commands compared with the committed schema or, with `--since <commit>`, with that commit's; `pnpm lint` runs `pnpm api:check`, which fails while they are stale; and `cf-os update` regenerates them whenever it moves the pin. `api` runs only inside a project, in the project's own copy, so even with `--url` its commands are those of the project's pin.

## A global `cf-os`

Installed globally (`npm i -g cf-os`), `cf-os` only scaffolds and updates. Inside a project it hands every other command to the project's own copy, so the deploy logic, and `api`'s commands, match the `cloudflare-os` version the project pins, the way a global `cf` defers to a project-local one.

`update` is the exception because it is what brings that copy up to date, so it runs in whichever copy you start. Use `npx cf-os@latest update` to get the newest; `pnpm cf-os update` runs the project's current one. It also runs outside a project: in a repository that pins Cloudflare OS without descending from the starter, `npx cf-os@latest update --upstream` is the whole interface, with nothing added to the repository but the ignored `.cf-os/`.
